# 01-05. Когда prototype становится уязвимостью

Ожидаемое время: 55 минут.

В предыдущей карточке поиск выше собственного объекта был полезен: все счётчики
делили метод из `Counter.prototype`. Но та же цепочка становится границей доверия,
когда программа без разбора копирует ключи из входного объекта. Цикл `for...in`
перечисляет и собственные, и унаследованные enumerable-свойства. В первом
примере объект `inherited` сам владеет настройкой `theme`.
`Object.create(inherited)` создаёт новый объект `input` и назначает
`inherited` его prototype, поэтому для `input` настройка `theme` уже является
унаследованной. Затем `input` получает собственную настройку `pageSize`. Массив
`seen` служит журналом перечисленных имён, а `key` — текущее имя, которое цикл
добавляет в этот журнал:

```js
const inherited = { theme: "dark" };
const input = Object.create(inherited);
input.pageSize = 30;

const seen = [];
for (const key in input) {
  seen.push(key);
}

console.log(seen); // ["pageSize", "theme"]
```

До цикла журнал пуст, а собственным ключом `input` был только `pageSize`;
действие `for...in` добавило в `seen` ещё и унаследованный `theme`. Вторая
причина связана не с перечислением, а с последующим присваиванием ключа.
`JSON.parse(text)` читает JSON-строку и возвращает JavaScript-объект. Ниже
результат разбора называется `payload`: у него появляется обычный собственный
ключ `"__proto__"` со значением `{ isAdmin: true }`. Пустой обычный объект
`result` — это назначение, в которое код затем копирует значение из `payload`;
поле `isAdmin` служит заметным маркером того, где закончится последующий поиск.
Такое начальное состояние ещё не означает, что prototype уже изменён. В
браузерах и в обычной конфигурации Node.js 24
присваивание значения такого ключа обычному объекту вызывает унаследованный
исторический accessor `Object.prototype.__proto__` и может заменить следующий
объект в его prototype chain. Этот accessor является normative optional: среда
выполнения вне браузера вправе его не предоставлять, а Node.js позволяет
отключить. После копирования выражение `Object.hasOwn(result, "isAdmin")`
проверяет, появился ли ключ непосредственно у объекта назначения, отдельно от
обычного чтения по цепочке:

```js
const payload = JSON.parse('{"__proto__":{"isAdmin":true}}');
const result = {};

result["__proto__"] = payload["__proto__"];

console.log(Object.hasOwn(result, "isAdmin")); // false
console.log(result.isAdmin); // true — значение найдено в новом prototype
```

Исходный код упражнения начинает с объекта стандартных настроек — `defaults` со
значениями `theme: "light"` и `pageSize: 20` — и поверх него переносит настройки
из пользовательского `input`. В упражнении нет сети и глобальной конфигурации:
тест передаёт локальные объекты и наблюдает только возвращённый результат. Этого
достаточно, чтобы различить показанные причины — унаследованный входной ключ и
собственный ключ, меняющий prototype результата. Вопрос карточки: какие ключи
вообще имеют право пересечь границу между непроверенным `input` и объектом
настроек?

## Две независимые поверхности

`for...in` перечисляет enumerable string keys объекта и его prototype chain. В
первом примере `theme` отсутствует у самого `input`, но цикл всё равно его увидит:

```js
const inherited = { theme: "dark" };
const input = Object.create(inherited);
input.pageSize = 30;

console.log(Object.keys(input)); // ["pageSize"]

for (const key in input) {
  console.log(key); // "pageSize", затем "theme"
}
```

Начальное состояние: own key у `input` только один. Действие: цикл проходит по
`input`. Наблюдение: результат включает унаследованный `theme`. Проверка
`Object.hasOwn(input, key)` могла бы отделить эту поверхность, но она ещё не
решает, разрешено ли копировать сам ключ.

Вторая поверхность видна на данных из JSON. Важно использовать `JSON.parse`:
в object literal особая историческая семантика есть только у невычисляемой
записи вида `__proto__: value` (и `"__proto__": value`) — она не создаёт тот же
own key. Вычисляемая запись `["__proto__"]: value` создаёт обычное свойство.

```js
const input = JSON.parse(
  '{"theme":"dark","__proto__":{"isAdmin":true}}'
);
const result = { theme: "light" };

console.log(Object.hasOwn(input, "__proto__")); // true
result["__proto__"] = input["__proto__"];

console.log(Object.hasOwn(result, "isAdmin")); // false
console.log(result.isAdmin); // true — найдено уже в новом prototype
```

До присваивания `result` наследуется от `Object.prototype`. В проверенной обычной
конфигурации Node.js 24 после присваивания исторический setter `__proto__` меняет
его prototype на объект из входа. Глобальный `Object.prototype` в примере не
изменён, но проверка вроде `if (result.isAdmin)` уже получает навязанное
значение. Этот конкретный механизм не обязан существовать в каждой среде
ECMAScript; allowlist ниже всё равно задаёт контракт входных ключей независимо от
наличия accessor.

## Почему allowlist является частью модели

Функция настроек знает свой публичный контракт: только `theme` и `pageSize` имеют
смысл. Поэтому безопасная граница начинается не с попытки перечислить все опасные
имена, а с небольшого множества разрешённых ключей. Затем копируются только
собственные enumerable keys входа, которые входят в это множество.

```js
const allowed = new Set(["theme", "pageSize"]);
const input = { theme: "dark", debug: true };

for (const key of Object.keys(input)) {
  if (allowed.has(key)) {
    console.log("accepted", key); // только "theme"
  }
}
```

`Object.keys` задаёт источник ключей, allowlist — полномочия каждого ключа. Это
разные проверки; пропуск любой из них меняет наблюдаемое поведение.

## Два правдоподобных неверных пути

1. Заменить `for...in` на `Object.keys`, но копировать всё. Унаследованные ключи
   исчезнут, однако собственный `"__proto__"` из JSON останется и изменит
   prototype результата.
2. Проверять только `key !== "__proto__"`. Это blacklist одного исторического
   имени, а не контракт настроек: неожиданные `constructor`, `isAdmin` или будущие
   ключи всё ещё попадут в результат. Allowlist отвечает на более устойчивый
   вопрос — какие поля нужны функции.
