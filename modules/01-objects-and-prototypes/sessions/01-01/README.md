# 01-01. Где JavaScript нашёл свойство

Ожидаемое время: 40 минут.

В прикладном коде объект настроек часто называют `config`, а выражение
`config.timeout` читают как «возьми из него поле `timeout`». Эта короткая
формулировка перестаёт работать, как
только программа получает значение, которого никто не записывал непосредственно
в `config`. Бывает и обратная неоднозначность: объект `state` владеет полем
`ready` со значением `undefined`, а ключа `missing` нет ни у него, ни у связанных
с ним объектов. И `state.ready`, и `state.missing` возвращают `undefined`, но
первый поиск останавливается на самом `state`, а второй — только на конце
prototype chain.

В первой лаборатории объект общих настроек называется `defaults`: его поле
`timeout` хранит число `3000`. Объект `service` связан с ним так, что при
отсутствии собственного поля поиск продолжается в `defaults`; у самого `service`
сначала есть только собственное поле `name` со строкой `"billing"`. Поэтому
чтение `service.timeout` возвращает `3000`: на `service` такого поля нет, и поиск
останавливается на `defaults`, где оно хранится. Вы проследите
каждую остановку этого поиска, а затем на трёх новых фрагментах спрогнозируете
прочитанное значение и объект, на котором поиск остановится. Вопрос карточки:
как доказать, на каком объекте JavaScript нашёл свойство, если синтаксис чтения
всегда выглядит одинаково?

## Результат и границы

После карточки вы сможете по конкретной цепочке предсказать результат чтения и
отличить собственное свойство от унаследованного и отсутствующего. В scope входит
только поиск обычных свойств для чтения; getters, setters и флаги descriptor мы
разберём в следующей карточке.

## Поиск идёт по цепочке

У каждого обычного объекта есть внутреннее поле `[[Prototype]]`: оно хранит
следующий объект поиска либо `null`, если продолжать цепочку некуда. Это не
скрытая копия свойств.
При чтении `service.timeout` JavaScript действует последовательно:

1. Ищет собственное свойство `timeout` у `service`.
2. Если свойства нет, переходит к `[[Prototype]]` объекта `service` и ищет там.
3. Повторяет переходы, пока не найдёт свойство или не дойдёт до `null`.
4. Если вся цепочка закончилась, результатом чтения становится `undefined`.

Такой маршрут называют цепочкой прототипов (`prototype chain`). В этой карточке
слово «прототип» означает именно следующий объект поиска. Свойство `.prototype`
у функций понадобится позже, когда мы разберём `new`.

Литерал `{}` создаёт обычный объект, следующим объектом которого по умолчанию
становится встроенный `Object.prototype`. Следующий объект самого
`Object.prototype` — `null`. Поэтому полная трасса отсутствующего поля у
`const record = {}` выглядит так: `record` → `Object.prototype` → `null`.

Метод `Object.getPrototypeOf(value)` показывает следующий объект цепочки, а
`Object.create(prototype)` создаёт новый объект и устанавливает переданный объект
как его `[[Prototype]]`:

```js
console.log(Object.getPrototypeOf({}) === Object.prototype); // true
console.log(Object.getPrototypeOf(Object.prototype)); // null
```

`Object.hasOwn(value, key)` отвечает, принадлежит ли ключ самому `value`, а
оператор `key in value` ищет ключ по всей цепочке. `console.log` здесь и далее —
канал наблюдения среды Node.js 24: оформление строки задаёт Node.js, а предмет
прогноза — вычисленные JavaScript-значения и результаты проверок.

### Сценарий 1: значение пришло из общих настроек

```js
const defaults = { timeout: 3_000, mode: "safe" };
const service = Object.create(defaults);
service.name = "billing";

console.log(service.name); // billing
console.log(service.timeout); // 3000
console.log(Object.hasOwn(service, "timeout")); // false
console.log("timeout" in service); // true
console.log(Object.getPrototypeOf(service) === defaults); // true
```

Исходно `defaults` владеет `timeout`, а новый `service` связан с `defaults` и
владеет только `name`. Чтение `service.name` заканчивается на первом объекте.
При чтении `service.timeout` первая проверка ничего не находит, зато следующая
останавливается на `defaults`. Поэтому значение равно `3000`, `hasOwn` возвращает
`false`, а `in` — `true`.

### Сценарий 2: собственное свойство закрывает унаследованное

В следующем фрагменте prototype содержит обычное записываемое свойство. Поэтому
присваивание `service.timeout = 1_000` создаёт собственное свойство у `service`;
оно не меняет `defaults.timeout`.

```js
const defaults = { timeout: 3_000 };
const service = Object.create(defaults);

service.timeout = 1_000;
console.log(service.timeout); // 1000
console.log(defaults.timeout); // 3000
console.log(Object.hasOwn(service, "timeout")); // true

delete service.timeout;
console.log(service.timeout); // 3000
console.log(Object.hasOwn(service, "timeout")); // false
```

После присваивания поиск останавливается на `service`: собственное свойство
затеняет (`shadows`) одноимённое свойство выше. Операция
`delete service.timeout` проверяет и удаляет только собственное свойство у
`service`: она не идёт по prototype chain и не удаляет `defaults.timeout`. На
следующем чтении путь снова доходит до `defaults`, и становится видимым прежнее
значение `3000`.

Есть важная граница: найденное свойство само может хранить `undefined`.

```js
const result = { value: undefined };

console.log(result.value); // undefined
console.log(result.missing); // undefined
console.log(Object.hasOwn(result, "value")); // true
console.log(Object.hasOwn(result, "missing")); // false
```

Одинаковое прочитанное значение не доказывает одинаковый путь. В первом случае
поиск успешно закончился на `result`; во втором он прошёл через `result`, затем
через `Object.prototype` и закончился на `null` без находки.

## Два правдоподобных неверных пути

1. Проверять наличие выражением `object.key !== undefined`. Свойство может
   существовать и намеренно хранить `undefined`, поэтому такая проверка смешивает
   найденное значение с фактом находки.
2. Использовать `key in object`, когда нужен именно владелец. `in` полезен для
   вопроса «доступен ли ключ через эту цепочку», но он не различает собственное и
   унаследованное свойство. Для вопроса владения нужен `Object.hasOwn`.
